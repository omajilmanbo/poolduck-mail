# ADR-011：人员与地点的 14 天延迟删除和恢复

- 状态：Accepted
- 日期：2026-07-28
- 相关 Issue：#104

## Context

当前人员和地点仅支持停用与重新启用。业务希望增加“删除”，但删除请求不能立即成为不可逆操作：

- 点击删除后进入 14 天恢复期；
- 恢复期内可恢复，并在 UI 显示剩余天数；
- 14 天后不可恢复并完成最终清理；
- 人员与地点仍关联扫码事件、邮件任务、未映射记录、operator 地点授权和审计记录。

现有 ADR-007 要求内部 UUID 和历史关联保持稳定，ADR-008 要求扫码、邮件和审计证据不可覆盖或删除。当前数据库也使用 `Restrict` 外键保护 `person_mappings`、`locations` 与 `mail_jobs` 等历史记录，因此不能把“最终删除”简单实现为级联物理删除全部关联数据。

## Decision

采用“14 天可恢复软删除 + 到期终结清理 + 最小历史墓碑”方案。

### 1. 状态与时间

- `locations` 和 `person_mappings` 新增 `deleted_at`、`purge_after`、`deleted_from_status`。
- 请求删除时由数据库时间写入 `deleted_at`，并令 `purge_after = deleted_at + 14 days`。
- `deleted_at IS NOT NULL AND purge_after > now()` 表示“待删除”。
- `purge_after <= now()` 表示恢复窗口已关闭；即使后台清理尚未执行，所有恢复和业务写入也必须拒绝。
- 剩余天数由服务端返回 `purge_after`，UI 按 `ceil((purge_after - now) / 24 hours)` 显示“剩余 N 天”，并同时展示最终删除日期。

### 2. 删除后的即时行为

- 删除人员或地点需要二次确认。
- 删除请求成功后，对象立即退出 active 业务路径；不得用于新扫码、人员写入、未映射处理或新邮件任务。
- 待删除对象仍显示在对应管理列表中，状态显示为“待删除”。
- 原“删除”按钮位置显示剩余天数；其右侧显示“恢复”按钮。
- 停用/启用与删除/恢复是不同操作。待删除期间不允许编辑、启用、停用或重复删除。
- 删除操作不得触发邮件。

### 3. 恢复

- 仅允许在 `purge_after` 之前恢复。
- 恢复后清空删除时间，并恢复到 `deleted_from_status` 记录的删除前状态；删除前为停用则恢复为停用，删除前为启用则恢复为启用。
- 人员恢复仍要求所属地点未处于待删除或已清理状态。
- 地点恢复保留恢复窗口内原有人员、历史与 operator assignments；服务端仍需按正常角色和地点权限校验。
- 到期后的恢复统一返回安全的不可恢复错误，不泄露跨 tenant 对象是否存在。

### 4. 地点与人员的关系

- 地点进入待删除后，其下人员立即不可用于业务操作，但人员不会分别启动新的 14 天计时器。
- 地点在 14 天内恢复时，其下尚未单独进入待删除状态的人员恢复原有状态。
- 地点最终清理时，终结清理其下仍存在的人员映射，并删除该地点的 operator assignments 和仅用于兼容解析的地点旧标识。
- 已经单独进入待删除状态的人员保留自己的 `purge_after`，但所属地点先到期时随地点一起完成终结清理。

### 5. 最终清理语义

- “最终删除”表示对象不可恢复、不可重新用于业务、当前 PII 被清除；不删除不可变扫码、邮件和审计历史。
- 人员终结清理：
  - 清除当前 `person_name` 和 `email`，写入非 PII 墓碑值；
  - 状态改为 `purged`；
  - `person_code` 永不复用，以保持历史关联与动作码失效；
  - 删除不再需要的当前业务兼容字段，但保留内部 UUID 关系墓碑。
- 地点终结清理：
  - 清除当前地点名称，写入非 PII 墓碑值；
  - 状态改为 `purged`；
  - `location_code` 永不复用；
  - 删除 operator assignments 和 legacy identifiers；
  - 保留内部 UUID 关系墓碑。
- `scan_events`、`mail_jobs`、provider 回执、上下文快照和 `audit_logs` 保持不可变；历史 UI 可以显示当时固化的名称，但不得把墓碑对象恢复为当前业务对象。
- 终结清理后，原地点名称可以重新创建；业务 ID 永不复用。

### 6. 执行与并发

- 后端增加周期性清理任务，使用数据库时间查找已到期对象并以小批次幂等处理。
- 所有业务查询和写入在读取对象时都必须把已到期对象视为不可恢复、不可操作，不能依赖清理任务是否准时运行。
- 删除、恢复和最终清理使用事务及条件更新；恢复与清理并发时以数据库 `purge_after` 为权威，到期后清理胜出。
- 清理任务失败可安全重试，并记录不含 PII 的计数、内部关联 ID 和失败原因。

### 7. 权限与审计

- location 删除、恢复仅允许当前 tenant 的 `tenant_manager`。
- person 删除、恢复允许当前 tenant 的 `tenant_manager`，以及对该 active location 有显式授权的 `operator`。
- 所有删除请求、恢复、过期恢复拒绝和最终清理都写审计记录。
- 对跨 tenant、伪造业务 ID、无 location assignment 和错误角色使用统一 not-found/forbidden 语义，不暴露对象状态。

## Alternatives considered

1. 14 天后物理级联删除全部历史
   - 不采用。会破坏 ADR-007/ADR-008 的历史追踪和审计约束，也与当前 `Restrict` 外键冲突。

2. 永久软删除，不执行到期清理
   - 不采用。不能满足 14 天后不可恢复和清除当前 PII 的要求。

3. 删除后保留业务可用性，只隐藏管理列表
   - 不采用。会造成隐藏对象继续扫码或发信，风险不可接受。

4. 恢复时一律启用
   - 不采用。可能把删除前已停用的对象意外恢复到可扫码、可发信状态。

5. 仅在 API 请求时惰性清理
   - 不采用。长期无人访问的到期数据不会及时清理；仍保留请求时的到期门禁作为后台任务延迟时的安全兜底。

## Consequences

- 用户有明确的 14 天纠错窗口，删除后立即停止业务使用。
- 管理 UI 需要展示待删除状态、剩余天数、最终删除日期和相邻恢复入口。
- 数据模型、所有人员/location 门禁、后台清理、审计、导出和测试均需同步修改。
- 最终清理保留最小关系墓碑和不可变历史，因此不是数据库级整行物理删除。
- 恢复地点可能同时恢复大量关联人员的可见性，确认文案必须明确影响范围。

## Migration impact

- 先以 nullable 字段扩展 `locations` 和 `person_mappings`，既有记录保持未删除。
- 新状态门禁上线后再开放删除 UI，避免旧服务把待删除对象当作 active 使用。
- 清理 worker 必须在字段和门禁部署完成后启用。
- 回滚不得清除 `deleted_at`、`purge_after` 或已经写入的审计记录；回滚版本必须继续把待删除/已到期对象视为不可操作。
- 迁移、回滚和合成数据验证需覆盖 active、inactive、待删除、到期未清理、purged 五类状态。

## Security impact

- 所有删除、恢复和清理查询必须从服务端认证上下文限定 `tenant_id`，person 还必须限定 location。
- 待删除与已到期对象不得通过扫码、幂等重放、邮件重试、历史详情、旧业务 ID 或 operator assignment 绕过门禁。
- 清理和审计日志不得记录完整人员邮箱、人员姓名、动作码负载或跨 tenant ID 映射。
- 最终清理不能修改历史邮件正文、provider 回执或扫码证据。

## Operational impact

- 新增清理任务运行次数、待清理数量、清理成功/失败数量和最老逾期时间监控。
- 部署文档需要说明清理任务的执行位置、批次、重试和故障恢复。
- 备份恢复后必须保留 `purge_after`，并立即重新执行到期门禁与清理，不能重新开放恢复窗口。
- 本地、CI 和 Staging 只使用合成人员与地点验证 14 天时间边界。
