# ADR-008：人员扫码进出动作由人员动作专用码决定

- 状态：Accepted
- 日期：2026-07-24
- 相关 Issue：#94, #68, #95

> 2026-08-06：ADR-015 supersede 本 ADR 的 `PD1|...` 负载语法与资产编码，改为上线前直接使用 `V2E<person_code>` / `V2X<person_code>`；本 ADR 的双动作来源、授权、幂等、去重、冲突、历史与邮件语义继续有效。

## Context

当前成功扫码统一创建固定“入室”邮件正文，扫码事件本身没有可信的进入/离开动作。仅根据人员最近一条记录自动交替，会在重复扫码、并发设备、漏扫、跨 location、跨日和人工修正后继续放大错误，并可能把错误动作写入历史或发送给收件人。

本决策需要在不依赖新门禁硬件的前提下，为每一次新扫码提供确定的动作来源，并与以下既有约束保持一致：

- ADR-002：人员识别和所有状态都必须限定在服务端确认的 `tenant + location` 上下文；
- ADR-003：只有 `trial`、`active` 可创建扫码和邮件任务，`expired`、`suspended` 必须继续阻断；
- ADR-004：MVP 只使用 sandbox/mock mail provider；
- ADR-006：`tenant_manager` 和 `operator` 只能在自己的 tenant 及授权 location 内扫码；
- ADR-007：人员业务码只用于定位，不能替代 tenant/location 授权；
- Issue #68：现有实现按同一 `tenant/location/scan_code` 的 10 秒重复提交返回原扫码事件和邮件任务；动作码上线时必须在解析后把该保护归一到 `person_code`，不能重复发信。

2026-07-24，业务负责人明确选择为每个人生成进入、离开两个动作专用码，并批准负载格式 `PD1|ENTRY|<person_code>` / `PD1|EXIT|<person_code>`。因此本 ADR 采用该方案并标记为 `Accepted`；#95 可按本决策进入实现，但不得扩大到真实邮件 provider、硬件门禁或考勤统计。

## Decision

新扫码的权威动作来源是人员动作专用码。服务端从扫码负载中的受支持格式解析 `person_code` 与动作，不接收客户端另行覆盖 `action`，也不根据上一条记录、时间、跨日边界或人员当前派生状态自动决定动作。

### 1. 动作与来源枚举

扫码事件的动作枚举固定为：

- `entry`：人员进入当前 location；
- `exit`：人员离开当前 location；
- `unknown`：动作来源缺失或无法可信还原，仅用于历史迁移、异常记录和人工调整前的展示。

动作来源枚举固定为：

- `person_action_code`：从已批准格式的人员动作专用码解析；
- `manual_adjustment`：`tenant_manager` 通过受控修正流程追加；
- `legacy_unknown`：历史记录无法可信还原。

`operator_selection`、`station_configuration` 和自动状态交替均不是本 ADR 下新扫码的有效动作来源。未来若改为操作员模式或固定方向设备，必须使用新的或 superseding ADR。

### 2. 动作专用码格式与解析规则

- 每个人只有一个 ADR-007 定义的规范 `person_code` 和一个人员数据库身份；进入、离开图片只是同一人员码的两个动作视图，不创建第二个 `person_id`、`person_code` 或人员映射。
- 两个逻辑负载固定为：
  - 进入：`PD1|ENTRY|<person_code>`
  - 离开：`PD1|EXIT|<person_code>`
- `PD1` 是大小写敏感的格式版本；`ENTRY` 和 `EXIT` 是大小写敏感的动作标记；`person_code` 必须按 ADR-007 规范化为大写 Crockford Base32。
- 解析后的 `ENTRY` 映射为 `entry`，`EXIT` 映射为 `exit`，动作来源记录为 `person_action_code`。
- 服务端只接受恰好三个以 `|` 分隔的字段。可移除扫码枪末尾的回车/换行和负载首尾空白，但不得删除字段内部空白、容忍额外字段或猜测未知版本/动作。
- 不支持的版本、未知动作、格式错误或裸 `person_code` 返回 `ACTION_CODE_INVALID`，不得创建成功扫码事件或可发送邮件任务；拒绝需要写安全审计。
- 动作码可以渲染为二维码或 Code 128。进入和离开图片必须除颜色外同时使用显著文字与图形标识，避免色觉差异或黑白打印导致混淆。
- 动作码不编码 `tenant_id`、`location_id`、邮箱或人员姓名。服务端必须在认证上下文和当前授权 location 内解析人员；持有码者不能据此跨 tenant/location 查询人员。
- 服务端确认格式、人员、tenant、location、订阅门禁和幂等结果后，把动作、来源和扫码事件在同一事务边界内持久化。邮件任务引用该已持久化动作；重试不得重新解析图片或重新判定。
- 客户端不得在动作码之外另传可覆盖动作的 `action`、`actor_id`、`tenant_id` 或动作来源。服务端从认证上下文记录实际操作者。

### 3. 状态机与异常语义

系统可为历史解释和异常提示派生人员在单个 `tenant + location` 内的状态：

| 前一派生状态 | 新事件动作 | 新派生状态 | 处理 |
|---|---|---|---|
| `unknown` | `entry` | `inside` | 允许；首扫不要求先有离开记录 |
| `unknown` | `exit` | `outside` | 允许；首扫不要求先有进入记录 |
| `outside` | `entry` | `inside` | 正常转换 |
| `inside` | `exit` | `outside` | 正常转换 |
| `inside` | `entry` | `inside` | 允许并标记同状态异常，不自动改成 `exit` |
| `outside` | `exit` | `outside` | 允许并标记同状态异常，不自动改成 `entry` |
| 任意状态 | `unknown` | 保持不变 | 不生成动作邮件，等待人工处理 |

派生状态不是新动作的权威来源，只用于历史解释、异常提示和人工排查：

- 首扫：显式动作直接生效，不猜测人员此前位于何处。
- 重复扫码：先执行幂等和 10 秒去重；被去重的请求不是新状态转换。
- 并发扫码：同一去重范围内只允许一个请求创建事件和邮件任务；后到请求不能翻转先到事件的动作。
- 漏扫：后续显式动作仍按原值记录；系统不得为补齐交替序列而改写动作。
- 跨 location：动作码只能在人员映射所属且当前授权的 location 解析。相同负载在其他 location 扫描时按未映射/无权处理，不发送邮件，也不改变原 location 的状态；不同人员映射的状态不得跨 location 共享。
- 跨日：无论 UTC 还是 tenant/location 本地时区的零点都不重置状态，也不改变动作码中的动作；展示时间按客户端时区转换，但排序使用服务端时间与稳定 ID。
- 同状态异常：10 秒窗口外的再次 `entry` 或再次 `exit` 仍是独立显式事件，可以生成对应邮件，但必须可审计并在历史中提示可能存在漏扫或误选。

### 4. 幂等键与 #68 去重

两层保护共同工作，优先级如下：

1. 请求幂等键
   - 客户端应为一次物理扫码生成不可预测的 `Idempotency-Key`。
   - 服务端先解析动作码，再按 `tenant_id + API route + Idempotency-Key` 限定唯一范围，并把键绑定到规范化请求指纹，至少包含内部 `location_id`、规范化 `person_code` 和解析出的 `action`。
   - 同键同指纹的重放在至少 24 小时内返回原 `scan_event` / `mail_job` 和 `deduplicated=true`，不得新建事件、改变动作或再次调用 provider。
   - 同键不同指纹返回冲突，不能复用原结果或创建第二个任务。

2. #68 的 10 秒业务去重
   - 即使客户端缺少幂等键或为重试错误生成新键，仍按已批准的同 `tenant/location/person_code` 10 秒窗口执行数据库并发保护。
   - 锁键和重复查询必须使用解析后的规范 `person_code`，不能使用包含 `ENTRY` / `EXIT` 的原始负载；否则同一人员的两张动作码会绕过冲突保护。
   - 窗口内动作相同，返回原事件/任务和 `deduplicated=true`。
   - 窗口内动作不同，返回动作冲突并引用原事件标识；不得创建第二个事件、第二个邮件任务或把原动作翻转。
   - 不同 tenant 或不同 location 不共享幂等记录、锁或派生状态。

幂等响应只返回已存在结果。若重放发生时订阅已变为 `expired` 或 `suspended`，可以读取原结果，但不能由重放触发发送或重试；邮件执行仍必须重新通过 ADR-003 的订阅门禁。

以下合成时间线用于审查边界；`T-A`、`L-1`、`P00000000001` 均为非真实标识：

| 时间 | 请求 | 预期结果 |
|---|---|---|
| `00:00.000` | `T-A/L-1`, `PD1\|ENTRY\|P00000000001`, key=`K-1` | 解析为 `entry`，创建事件 `E-1` 和唯一邮件任务，派生状态为 `inside` |
| `00:02.000` | 相同 payload，key=`K-1` | 幂等重放返回 `E-1`，`deduplicated=true`，不再次调用 provider |
| `00:04.000` | 相同 payload，key=`K-2` | #68 兜底返回 `E-1`，不创建第二个事件或任务 |
| `00:05.000` | `T-A/L-1`, `PD1\|EXIT\|P00000000001`, key=`K-3` | 按同一 `person_code` 命中 10 秒动作冲突，拒绝且不翻转 `E-1` |
| `00:10.000` | `T-A/L-1`, `PD1\|EXIT\|P00000000001`, key=`K-4` | 已到窗口边界，创建 `E-2`，派生状态为 `outside` |
| `00:11.000` | 在未映射的 `T-A/L-2` 扫 `PD1\|EXIT\|P00000000001`, key=`K-5` | 按未映射处理，不发信且不改变 `L-1` 状态 |
| 次日 `00:00.000` | `T-A/L-1`, `PD1\|ENTRY\|P00000000001`, key=`K-6` | 跨日不重置或推断动作；记录动作码中的 `entry` |
| 任意时间 | `tenant_manager` 为漏扫追加 `exit` adjustment | 追加人工补录并重算派生状态，不创建或重发邮件 |

并发审查同时扫描同一人员的两张动作码：数据库事务锁必须按规范 `person_code` 串行化；只允许第一个请求创建事件/任务，相同动作的后到请求返回原结果，相反动作的后到请求返回冲突。不同 tenant 或不同 location 的并发请求不得等待或命中对方的记录。

### 5. 人工修正与审计

- 仅 `tenant_manager` 可执行动作修正；`operator` 可查看自己有权访问的异常，但不能改写历史。
- 修正必须追加不可变的 adjustment 记录，包含原动作、修正后动作、原因、修正人、记录时间和目标事件。禁止覆盖或删除原事件、原来源、原操作者、原邮件正文和 provider 回执。
- 错误动作使用 `replace_action` adjustment；漏扫使用带声明发生时间的 `insert_missing_action` adjustment。后者明确标记为人工补录，不能伪装成设备扫码。
- 修正和补录都不得自动创建或重发邮件。若未来需要发送更正通知，必须使用独立 Issue 和人工批准的文案/收件规则。
- 派生状态按当前有效动作和人工补录重新计算，但历史查询必须同时展示原始值和修正标记，确保审计可追溯。
- 修正只能作用于同 tenant 的记录，并继续受 location 授权限制；不得通过修正移动事件的 tenant、location、person 或 mail job 关联。

### 6. 邮件文案与历史展示

固定邮件正文从同一个已持久化动作生成：

- `entry`：`{tenant_name}，{location_name}からのお知らせ：{person_name}　さんは　{time_stamp}　に入室しました。`
- `exit`：`{tenant_name}，{location_name}からのお知らせ：{person_name}　さんは　{time_stamp}　に退室しました。`
- `unknown`：不创建动作邮件任务。

历史记录显示：

- `entry` → “进入”；
- `exit` → “离开”；
- `unknown` → “动作未知”；
- 被修正事件显示有效动作，同时明确标记“已修正”并允许有权限的用户查看原动作、修正原因和审计信息；
- 被 #68 去重的请求不增加历史行，原事件保持唯一。

现有历史记录不能根据固定“入室”邮件正文反推真实动作。迁移时应标记为 `unknown + legacy_unknown`；已发送邮件正文和 provider 回执保持原样，历史界面需说明旧记录动作不可确认。

### 7. 后续实现边界

#95 及其实现拆分需要覆盖以下范围：

- 数据库：动作、来源、请求幂等记录、同状态异常和 append-only adjustment；不得破坏现有事件/邮件追溯。
- API：单一扫码负载输入、动作码格式校验、幂等键重放/冲突、历史动作和修正接口；不接受独立 `action` 覆盖，错误响应不得泄露跨 tenant 资源是否存在。
- Backend：版本化动作码解析、事务内持久化、按规范 `person_code` 集成 #68 并发去重、邮件模板选择、重试复用原动作、tenant/location/订阅门禁和审计。
- Frontend：展示解析后的进入/离开结果、历史动作/异常/修正和 `tenant_manager` 修正流程；扫码工作台不提供可覆盖动作码的手动模式选择。
- 图片生成：基于同一 `person_code` 生成进入/离开两个逻辑负载，使用清晰的文字和非纯色彩区分；图片不包含人员邮箱、tenant/location 或内部 UUID。
- 测试：使用合成时间线覆盖首扫、重复、并发相同/相反动作、漏扫、跨 location、跨 tenant、跨日、订阅变化、人工修正和 mail retry。

真实邮件 provider、入口/出口硬件接入、考勤统计、操作员模式、自动交替和更正通知均不属于 #95。

## Alternatives considered

1. 根据人员最近状态自动在 `entry` / `exit` 间交替
   - 未选择。重复、并发、漏扫和跨设备会永久改变后续推断，并可能直接产生错误邮件。

2. 仅按 10 秒时间窗口判断动作
   - 未选择。时间窗口只能判断是否可能重复，不能证明人员进入或离开；它继续作为防重复发信保护。

3. 为入口/出口设备或扫码站配置固定方向
   - 未选择。单张人员码即可工作，但当前没有设备身份、注册、部署位置和防篡改前提，且本 Issue 不允许引入硬件集成。

4. 操作员在页面选择或扫描公共“进入/离开模式码”
   - 未选择。可以让每个人只保留一张码，但模式可能残留、忘记切换或被另一名操作员改变；动作专用人员码把动作和人员绑定在同一次物理扫码中。

5. 根据人员跨 location 的最近记录推断
   - 未选择。会扩大租户/location 数据耦合，无法区分真实移动、漏扫和同名/映射问题，并违反 location 内独立判定原则。

6. 对未知动作继续使用“入室”文案
   - 未选择。会把未知事实伪装成已确认进入并触发错误通知。

## Consequences

正面影响：

- 每个新事件的动作来源明确，邮件、历史和审计可以引用同一持久化结果；
- 扫描动作码即可完成动作选择，不需要操作员额外点击或维护会话模式；
- 重放、并发和 mail retry 不会重新推断或翻转动作；
- 首扫、漏扫、跨 location 和跨日不再依赖脆弱的交替假设；
- 旧记录和人工修正保留原始证据，不会伪造历史；
- 不依赖新增门禁硬件即可实施。

负面影响：

- 每个人需要维护进入、离开两个逻辑动作码；打印、发放和重新生成成本增加；
- 操作员仍可能拿错或扫错动作图片，因此图片必须使用显著文字/图形区分，状态机仍要提示同状态异常；
- 10 秒内真实发生的相反动作会被冲突保护拦截，需要操作员等待窗口结束或由管理员审查；
- 同状态异常在窗口外仍可能生成动作邮件，系统只能提示而不能替业务人员改写事实；
- 幂等键和 adjustment 需要新增持久化、API、审计和测试成本；
- 旧记录将显示“动作未知”，不能从历史固定文案恢复真实进出状态。

## Migration impact

- 不修改或删除现有 `scan_events`、`mail_jobs` 和 provider 回执。
- 为现有扫码事件回填 `unknown + legacy_unknown`，不得依据固定“入室”正文回填 `entry`。
- 新字段应先 nullable 扩展、分批回填，再对新事件启用必填约束；迁移必须可重入并记录合成统计，不输出完整邮箱或扫码载荷。
- 为每个已有规范 `person_code` 生成 `PD1|ENTRY|...` 和 `PD1|EXIT|...` 两个逻辑动作码；图片可以确定性重新生成，不新增人员身份或动作码数据库主键。
- 切换前必须完成动作图片生成、发放和合成扫码验证。切换后裸 `person_code` 不再创建动作邮件，统一返回 `ACTION_CODE_INVALID`；不得在同一入口静默把裸码解释为 `entry`。
- 历史邮件保持原正文；前端和导出必须区分“当时发送文案”和“当前有效动作”。
- 发布需要支持回滚到旧读取路径，但回滚不得删除已经记录的动作、幂等键或 adjustment。

## Security impact

- 动作、幂等键、派生状态和 adjustment 都必须以服务端认证的 tenant/location 范围查询和写入，禁止全局按人员码或事件 ID 查找后再比较 tenant。
- 动作码是公开定位负载而不是凭据；复制、拍照或手工构造负载不能绕过登录、角色、tenant/location 授权、订阅门禁或去重。
- 服务端只从负载解析动作并从认证上下文记录操作者；客户端不能另行指定动作、修正人、tenant 或动作来源。
- `tenant_manager` 修正需要强制原因和审计；敏感日志不得包含完整人员邮箱、邮件正文、未脱敏 scan code 或跨 tenant 标识映射。
- 订阅门禁仍在创建事件、创建邮件和每次发送/重试前执行；幂等重放不能绕过门禁触发 provider。
- `unknown`、冲突和修正默认不发信，降低错误动作或错误收件人通知风险。

## Operational impact

- 需要监控动作码格式/版本拒绝、裸人员码拒绝、同状态异常、10 秒动作冲突、幂等键指纹冲突、人工修正和未知历史记录数量。
- 排障按 tenant、location、事件 ID、幂等结果和动作来源定位；日志使用内部关联 ID 或掩码，不输出 PII。
