# 功能需求初稿

## 1. 系统定位

本系统是一个面向租户客户公司的 Web SaaS。
客户通过扫码枪扫描条码/二维码，系统根据扫码结果找到对应邮箱并发送邮件。
系统支持多租户，并允许每个租户维护自己的用户、订阅、办公室/学校、扫码编号与邮箱对应关系。

---

## 2. 一级功能模块

### 2.1 租户功能管理

租户管理员登录系统后，可以进入租户功能管理页面，管理本租户的基础数据和功能模块。

包含以下子模块：

- 维护用户账号订阅
- 新增或删除办公室/学校
- 维护扫码编号与邮箱对应关系（人员一览）
- 扫码邮件（核心功能）
- 群发邮件

---

## 3. 各模块需求

### 3.1 维护用户账号 / 地点

管理员（`tenant_manager`）可以：

- 新增、编辑、启用或停用 `operator` 账号，并执行受控密码重置
- 管理本 tenant 的 `operator`；当前不能创建或管理其他 `tenant_manager`
- 创建和重置密码由 `tenant_manager` 提交；密码至少 8 位且必须同时包含英文字母和数字，可包含额外符号
- 用户管理页仅向 `tenant_manager` 展示；角色固定为 `operator`，停用与密码重置前必须明确确认，密码不得持久化在浏览器或列表中显示
- 只读查看本 tenant 的基础订阅状态；MVP 不允许 `tenant_manager` 调整套餐或订阅状态
- 新增、编辑、启用或停用地点
- 新增地点只填写名称；地点 ID 由服务端生成 8 位大写 Crockford Base32，技术类型固定为 `location`
- 地点与人员均支持停用后重新启用，且保留原 ID 与历史关联
- 地点与人员也支持独立删除：删除后立即停止业务使用，14 天内可恢复到删除前状态；到期后匿名化
  当前资料并永久禁止恢复，公开 ID 与不可变扫码、邮件和审计历史不得删除或复用

该功能需要管理员权限。

MVP 不建设商业订阅概览、套餐 allowance、价格、用量计费或续订管理页面。订阅
`status` 与 `end_at` 仅用于扫码和邮件发送的安全门禁；商业化计费由未来 Issue #102
独立规划，不得成为地点、人员、扫码、邮件、历史或权限功能的前置条件。

普通用户（`operator`）限制：

- 不可维护用户账号
- 不可调整订阅状态
- 不可新增/删除办公室或学校
- 仅可维护人员一览（扫码编号与邮箱映射）

详细规则待后续补充。

---



#### 3.1.1 location 数量与商业化边界（MVP）

- MVP 不按 location 数量或活动人员数量执行商业配额、收费或 proration。
- location 创建、停用和重新启用只执行 tenant scope、角色、状态、输入与数据完整性校验，
  不要求价格、套餐 allowance、付款或计费批准。
- 订阅 `expired` / `suspended` 的安全门禁仍按 ADR-003 执行，但该门禁不定义
  location 数量或人员数量。
- 未来商业化如需按启用 location 或活动人员计费，必须通过 #102 的新 ADR 和独立实现
  Issue 引入，不得追溯性阻塞或改变当前非商业化功能。

### 3.2 维护扫码编号与邮箱对应关系（人员一览）

管理员可以维护人员一览数据，至少包含：

- 扫码编号
- 姓名
- 所属办公室/学校
- 对应邮箱地址
- 状态（启用/停用）

### 3.3 扫码邮件（核心功能）

扫码邮件是 MVP 的核心功能。

#### 3.3.1 前置条件

- 用户已登录系统
- 用户已选择办公室/校舍
- 当前租户订阅状态为有效
- 扫码编号与邮箱对应关系已维护
- 人员具有分别表示进入与离开的两张动作码：`V2E<person_code>`、`V2X<person_code>`
- ADR-015 已直接替换旧格式，不实施双读或旧资产迁移；每人仍只有一个 `person_code`、两张逻辑动作码、四张本地生成资产，tenant/location 授权继续由服务端决定

#### 3.3.2 订阅限制

统一订阅状态集合：`trial` / `active` / `expired` / `suspended`。

当租户订阅状态为：

- `trial` 或 `active`：允许扫码和发送邮件
- `expired` 或 `suspended`：禁止扫码提交与邮件发送（包括手动创建/重试邮件任务）

#### 3.3.3 页面显示（UI/UX）

进入扫码邮件页面后，系统必须展示以下信息区块：

- 办公室/校舍切换控件（必选，未选择时禁用扫码提交）
- 扫码输入区域（接收扫码枪条码/二维码）
- 发送交互按钮预留位（当前支持扫码枪输入后自动发送，或回车触发发送，无需人工点击）
- 最近扫码/邮件发送结果列表（含“进入/离开/动作未知”与成功/失败状态）
- 异常提示区（用于展示未找到邮箱、发送失败、订阅不可用等错误）

订阅状态展示规则：
- 扫码发送页面不显示“剩余订阅时间”提示
- 订阅状态为 `expired` / `suspended` 时，页面必须显示限制提示并禁用发送能力
- 续订提醒与订阅数量展示统一放在“租户功能管理”页面

MVP 页面不提供邮件正文自定义编辑区，也不提供扫码发送前的正文预览。

#### 3.3.4 邮件正文规则

MVP 阶段邮件正文由系统根据动作码中的明确动作生成：

```text
entry:
{tenant_name}，{location_name}からのお知らせ：{person_name}　さんは　{time_stamp}　に入室しました。

exit:
{tenant_name}，{location_name}からのお知らせ：{person_name}　さんは　{time_stamp}　に退室しました。
```

变量来源定义：

- `{tenant_name}`：租户公司名
- `{location_name}`：当前办公室/学校名
- `{person_name}`：扫码编号对应人员姓名
- `{time_stamp}`：该次动作的接收时间，按 UTC 生成 14 位 `yyyymmddhhmmss`

重复扫码规则：同一 tenant、location、解析后的 `person_code`、同动作在 10 秒内的重复提交返回首次创建的 scan event/mail job，并标记 `deduplicated=true`，不得创建第二个可发送任务；相反动作返回 `SCAN_ACTION_CONFLICT`，不写入第二条记录或任务。

请求幂等规则：客户端可发送 `Idempotency-Key`。同 key 与相同规范请求在 24 小时内返回首次结果；同 key 绑定不同 location、人员或动作时拒绝。邮件重试始终复用首次写入的动作与正文。

示例：

```text
A公司，B办事处からのお知らせ：C员工　さんは　20260520143000　に入室しました。
```

说明：用户自定义邮件文本不属于当前 MVP 范围，作为后续扩展候选保留。

#### 3.3.5 扫码流程（页面操作顺序）
1. 用户进入扫码邮件页面
2. 用户选择或切换办公室/校舍
3. 系统检查当前租户订阅状态
4. 若订阅为 `trial` / `active`，启用扫码输入
5. 用户使用扫码枪扫描该人员的 ENTRY 或 EXIT 条码/二维码
6. 系统严格解析 `V2` 版本、`E`/`X` 动作与 `person_code`，并在当前 tenant/location 查找对应邮箱
7. 系统按同一动作生成固定格式邮件正文（后端内部处理）
8. 系统触发发送并回写发送结果

#### 3.3.6 找到对应邮箱时
1. 创建扫码记录并固化 `action` 与 `action_source=person_action_code`
2. 创建邮件发送任务并固化相同动作
3. 系统按该动作生成“入室”或“退室”固定正文
4. 系统向对应邮箱发送邮件
5. 记录邮件发送结果
6. 管理员可以查看历史记录并导出

#### 3.3.6a ADR-017 发送犹豫期

1. T0 使用数据库时间原子创建不可变扫码证据和唯一 `waiting` 邮件任务；截止前 10 秒 provider 不得调用。
2. 同 location 当前授权 operator 或 tenant_manager 可在截止前取消，无需自由文本原因；恰好截止时发送领取优先。
3. 取消成功使原动作从当前派生进出状态中失效，并把任务置为 `canceled`；原始动作、邮件快照、幂等、审计和 provider 证据继续保留。
4. 取消后使用新 `Idempotency-Key` 可立即重扫正确动作；原 key 只返回已取消的原结果。
5. 首次 `cancel_until/send_not_before` 与失败重试 `scheduled_at` 独立；每次实际发送仍重新执行订阅与资源门禁。
6. 本地代码已实现 1 秒 worker、取消 API 和工作台按钮；这不表示任何 Staging/Production 环境已部署。

#### 3.3.7 未找到对应邮箱时
1. 对格式正确但未映射的动作码提示“未找到对应邮箱”，并保持在当前页面
2. 不创建 scan event、未映射 case、邮件发送任务或逐请求数据库审计，不触发发送
3. 不区分 inactive、pending deletion、purged、其他 location、其他 tenant 或随机合法码，不泄露人员是否存在
4. 客户端不能指定、复用或恢复任意 `person_code`；人员重新启用或恢复仍从人员管理执行

#### 3.3.8 邮件发送失败时
1. 系统在异常提示区展示“邮件发送失败”及可识别失败原因
2. 最近扫码/发送结果列表标记该次任务为失败
3. 保留扫码与任务记录，按 30 秒、2 分钟、10 分钟自动重试；三次重试耗尽后保留终态失败用于排障

#### 3.3.9 订阅过期/暂停时页面限制
1. 当订阅状态为 `expired` 或 `suspended`，页面仍可访问但必须显示限制提示
2. 禁用扫码输入与提交动作
3. 禁止创建邮件任务与发送动作
4. 引导用户联系管理员处理订阅状态

## 4. 当前已确定的业务规则

### 4.1 多租户
- 每个客户公司是一个租户
- 每个租户有独立的数据范围
- 用户只能访问所属租户的数据
- 登录流程采用三步：输入公开 `tenant_code` → 输入“用户名/邮箱”和密码 → 进入业务界面
- operator 必须有 tenant 内唯一 username、email 可空；tenant_manager 必须有 email 且只能用邮箱登录
- identifier 含 `@` 时只查邮箱，否则只查 operator username，不跨字段或跨 tenant 回退
- tenant 不存在、身份不存在、账号停用或密码错误统一提示登录失败，不暴露具体失败阶段
- 后端必须把 `tenant_code` 解析为内部 tenant UUID 并校验用户归属；登录成功后业务接口仍以后端会话中的 tenant 上下文进行隔离，客户端不能提交 UUID 切换 tenant

### 4.2 办公室/学校维度
- 一个租户可以有多个办公室/学校
- 扫码邮件操作前，需要先切换当前办公室/校舍
- 邮件内容中需要体现办公室/学校名

### 4.3 邮件文本
MVP 阶段：
- `entry` 正文固定以“入室しました。”结束，`exit` 正文固定以“退室しました。”结束
- 进入/离开只由两张人员动作码显式决定，不提供操作员手动切换，也不按租户时区零点、每日扫描次数或上一条状态推断
- 旧记录保留 `unknown` / `legacy_unknown`，不得反推动作
- 不允许前端传入自定义正文覆盖固定格式
- 用户自定义邮件文本作为后续扩展候选，不进入当前 MVP

### 4.4 异常处理
- 若扫码结果找不到对应邮箱，不发送邮件
- 需要记录异常扫码事件
- 裸 `person_code`、未知版本/动作或格式错误返回 `ACTION_CODE_INVALID`，不写入扫码事件或邮件任务
- 管理员需要能够后续确认和修正人员信息
