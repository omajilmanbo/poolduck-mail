# A11 旧人员码回填与两个后端进程同秒创建

2026-11-20（日本时间）· 候选 `a05251897d7fc11d96114606bcaa1807dd96af55` · 本机 PostgreSQL 16.16

**旧数据回填和双进程同秒创建均通过。** 2 个合成租户的 3 个地点各有一名人员使用同一个旧扫码值。升级后，4 条旧扫码和 4 个已发送邮件任务全部匹配原人员、地点及租户。两个独立候选后端随后在同一真实 UTC 秒内各创建 2 名人员，4 个响应中的人员公码逐一匹配数据库，最终全库 8 个公码全部唯一。本次未观察到自然碰撞。

## 旧数据从哪里来

使用引入目标迁移的提交 `c2bf9d0` 的直接父提交 `17685f8844e1da46517d06e1d515b3b2226ba2c2`。在其第 1 条迁移建立的旧结构中，用该版本生成的 Prisma Client 建立 2 个有效订阅、2 个旧经理账号、3 个地点和 4 条人员映射。旧角色 `root_admin` 随正式迁移转为 `tenant_manager`。

| 旧数据 | 合法业务输入 | 形成的历史 |
| --- | --- | --- |
| 租户 A，地点 1 | active 人员，使用共用旧扫码值 | 同一人员正常扫码 2 次，生成 2 个独立事件和 2 个邮件任务 |
| 租户 A，地点 2 | 另一名 active 人员，使用相同旧扫码值 | 1 个事件、1 个任务 |
| 租户 B，地点 1 | 第三名 active 人员，使用相同旧扫码值 | 1 个事件、1 个任务 |
| 租户 B，地点 1 | 独立旧码的 inactive 人员 | 无扫码或邮件历史，仍应获分配公码 |

两个账号各通过旧版 `POST /api/auth/login` 正常登录，在各自有权访问的地点读取人员清单。4 条事件均由旧版 `POST /api/scan-events` 写入，4 个任务从 queued 经旧版 `POST /api/mail-jobs/{id}/send` 使用 sandbox 成为 sent。逐次将两个接口返回的事件 ID、任务 ID 和 mock 回执与数据库比对。旧人员数据通过历史模型建立，扫码、邮件及回执均来自实际业务调用。

## 逐条对账

| 检查点 | 实测结果 |
| --- | --- |
| 第 1 条后至第 4 条后，紧邻目标迁移之前 | 人员公码、扫码人员外键和邮件上下文快照列尚不存在。用旧租户、地点和扫码值组成的三元组解析每一条历史，4 条扫码各命中 1 个正确人员和 1 个已发送任务。按主键排序的旧事实在两个检查点相同。 |
| 第 5 条 `20260724000000_add_person_codes_and_mail_context` 后 | 4 条旧映射均保留原 UUID、租户、地点、旧兼容 `scan_code`、姓名、邮箱、状态和创建时间。4 个新 `person_code` 都是 12 位大写 Crockford Base32，互不相同。逐个独立解码前 7 位，均等于该旧映射 `created_at` 的 Unix 秒。无历史的停用人员也正确回填。 |
| 同一检查点的扫码和邮件 | 4 条扫码保留各自原主键、租户、地点、操作人、接收时间、扫码类型和原始载荷。`scan_events.scan_code` 与 `person_code_snapshot` 均为其人员的新码，`person_mapping_id` 为原人员 UUID。4 个邮件任务均保留原任务 ID、扫码外键、收件地址、主题、正文、sent 状态、发送时间和旧 mock 回执。新增地点与人员外键及租户名、地点名、人员名、公码四项快照分别匹配正确对象，来源均为 `legacy_backfill`。 |
| 完成全部 21 条迁移 | 所有上述旧事实、新码、外键与快照逐行一致。4 条历史动作均为 `unknown / legacy_unknown`，邮件动作快照为 `unknown`。两个租户的候选人员清单抽查也返回回填公码。旧版回执保存在邮件任务上，候选投递尝试表为 0 行。 |

目标迁移的人员码全局唯一索引已在实库核实。索引有效、只包含 `person_code`、没有过滤谓词，列为 NOT NULL。最后一次独立只读 SQL 按内部主键、租户、地点及公码连表，匹配 4 条历史链、3 名有扫码的人员、3 个地点、2 个租户和 4 个不同的旧 mock 回执。[目标迁移 SQL](../../backend/prisma/migrations/20260724000000_add_person_codes_and_mail_context/migration.sql) · [数据库字段说明](../database.md)

## 双进程同秒创建

在同一个新建 PG16 上启动两个独立的 `node dist/main.js` 操作系统进程，核实 PID 不同，分别监听两个隔离端口并通过健康检查。两个租户的经理分别向自己的后端登录，并用独立会话请求 `GET /api/auth/me` 核对归属。等待数据库时钟自然进入下一秒后，每个进程通过 `POST /api/locations/{location_code}/people` 接收两次正常创建，输入仅为合成人员姓名和邮箱。

| 观察项 | 实测结果 |
| --- | --- |
| 真实同秒 | 4 次均返回 201。首个请求前和所有响应后的数据库时钟读数均在 `2026-11-19 20:45:28 UTC`，两次采样相隔 299 ms。4 行 `created_at` 的最大差为 5 ms。4 个公码的前 7 位分别解码为同一秒。 |
| 返回码及归属 | 4 个返回码各对应唯一新行。按各自请求比对响应的人员码、兼容公开 ID 和地点码，再比对数据库公码、内部人员 UUID、所属租户／地点、姓名及邮箱，4 条均匹配。最终 8 条人员映射、8 个不同公码。 |
| 随机碰撞 | 专用 PG 服务日志中，命名该公码唯一索引的重复键错误为 0。候选中公码重试耗尽审计为 0。本轮样本为 4 次正常创建。 |
| 既有单元测试 | 独立运行 2 个测试套件，筛选后 4 项通过、10 项未选中。3 项覆盖格式、跨秒排序和单进程同秒去重。另 1 项模拟一次 Prisma `P2002`，第二次创建返回 201，审计中无被拒公码。此条属于模拟碰撞的重试证据。[生成器测试](../../backend/test/person-code.spec.ts) · [管理测试](../../backend/test/management.spec.ts) |

## 复核与适用范围

在同一新建 PostgreSQL 16 库上，依次核对第 1、4、5、21 条迁移的完成账本和 SQL 校验和。由两个独立进程在同一数据库秒各发起两次正常 HTTP 创建，按返回的人员公码和数据库主键核对租户、地点、唯一性及历史关联。以上是合成数据。自然碰撞、负载和跨机时钟偏差仍待独立取证。一次碰撞后的成功重试由既有用例模拟。
